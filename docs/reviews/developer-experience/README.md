# Матрица мнений и план улучшения опыта разработчика

Дата: 12 октября 2026 года. Основа: commit `4221dcb`.
Статус: инженерная реализация DX-01—DX-09 выполнена; локальные quality gates проходят.
Результаты и открытый пользовательский пилот описаны в [resolution](resolution.md).

Шесть независимых агентов рассмотрели текущий код, руководства и тесты.
Линзы Taylor Otwell и DHH моделируют удобство API и простоту сопровождения.
Это не реальные мнения, участие или одобрение этих людей.
Остальные четыре роли моделируют разработчиков-пользователей; реальные интервью пока не проведены.

Предыдущие решения из [second-pass](../second-pass/resolution.md) учитываются как действующие контракты.
Интеграционные ограничения, уже описанные в документации, не объявляются заново неисправленными багами.
Критерии ниже сохраняют согласованный план; это не протокол выполненных проверок.

## Решения руководящих линз

1. Сначала сделать существующий путь удобным: цельный пример, troubleshooting и диагностика.
2. Сохранить входящие verb/CSRF/ACL проверки перед блоком Strangler filters.
   Они должны действовать и при выключенной функции; проверка только внутри прокси этого не обеспечивает.
3. Сохранить действующее распространение исключений `afterAttempt()` для обязательных hooks.
   Наблюдение показывать отдельным application recipe с обработкой ошибки; новый observer пока не вводить.
4. Для независимого rollout использовать существующие feature keys и два filters.
   Формулировку «Strangler последний» уточнить: весь блок Strangler filters находится после проверок доступа.
5. Не строить DTO/event bus, новую авторизацию, tracing platform, circuit breaker или config framework.
6. Не добавлять retries, replay в Yii, dual writes, автоматическую миграцию данных или следование redirects.
7. Проверять пользовательский результат, а не только сохранение 100% coverage/MSI.

Отличие от предыдущего бизнес-ревью: incoming-method API, per-route flags и безопасный observer не являются
первыми обязательными изменениями. Для них сначала нужно показать ограничение существующего решения.
Data ownership, доступ и идемпотентность остаются интеграционными обязанностями, но получают рабочие примеры.

### DX-01. Один запускаемый пример

Использовать PHP, Composer и существующие зависимости; не требовать Docker или новых сервисов.
Два локальных HTTP entry points: настоящий Yii host и небольшой backend.
Для демонстрации совместного чтения использовать SQLite и одну явно описанную совместимую модель данных.
Для этого примера отдельно требуется `pdo_sqlite`; указать его в prerequisites,
не добавляя SQLite как обязательную зависимость самой библиотеки.
Это модель примера, а не рекомендуемое устройство всех production deployments.

Готово, когда из чистого checkout пользователь устанавливает зависимости и запускает пример
без придумывания недостающих классов, настроек и endpoint.
При выключенном флаге виден legacy ответ; при включённом — совместимый ответ через backend и `X-Strangler: 1`.
CI запускает доставляемый пример, а не отдельную копию адаптера из tests fixtures.
Документация ссылается на исходники примера; существующие проверки snippets не теряются без замены.

### DX-02. Завершённые входные контракты

Дать два варианта: JSON и HTML-форма `item[...]`.
В form-варианте validation filter и `payloadUsing()` используют один application-owned источник
проверенного ввода. Не угадывать формат тела автоматически.
Добавить таблицу: checks в action/`beforeAction()` переносятся в pre-filter;
необходимый cleanup из `afterAction()`/`postFilter()` получает проверенный `onEndRequest` recipe.

Готово, когда при off/on одинаково отвергаются неверный метод, отсутствующая авторизация,
чужой ресурс, неверный CSRF, `item=string` и конфликт request `id` / body `ID`.
Каждый отказ происходит до legacy action и HTTP-вызова backend.
Разрешённый старый POST выполняет один upstream PUT.
Cleanup срабатывает один раз для legacy, proxied и denied запросов.
Необходимые для примера security filters реализованы в host-приложении.

### DX-03. Старый клиент получает свои имена полей

Текущий пример переводит `NAME` в `product.title`, но возвращает backend `errors` напрямую.
Источник: [api-adaptation.md](../../api-adaptation.md), методы `transformPayload()` и `transformResponse()`.
Добавить явную обратную таблицу имён и заранее выбрать поведение неизвестных ключей:
показывать как общую ошибку или сохранять по явно описанному контракту.
Не терять неизвестные ошибки молча.

Готово, когда backend validation error подсвечивает соответствующее поле старого клиента;
проверены nested paths, несколько сообщений, неизвестное поле и package-generated error.
Статус остаётся ошибочным. Универсальный автоматический field mapper не нужен.

### DX-04. Диагностика без неоднозначности и секретов

Причины: `feature_disabled`, `route_unmapped`, `bypass_callback`, `bypass_payload`, `forwarded`.
Добавить `feature`, `action`, `request_id`, `upstream_status`, `client_status` и длительность.
Статусы и длительность относятся к реально выполненному attempt и отсутствуют у неподходящего кандидата.
Отдельно обозначать transport failure и ошибку адаптации; для последних client status может ещё не существовать.

При двух фильтрах отказ первого кандидата не означает исполнение в Yii: следующий фильтр может перенаправить запрос.
Поэтому reason-log описывает решение конкретной feature/filter и `selected=false`, а не ложный `executor=legacy`.
Выбранный upstream executor фиксируется при forwarding. Финальное legacy execution проверяет host-пример.
Диагностика не вызывает reader или callback повторно и не создаёт отдельного event framework.

Для обычного журнала использовать route template, а не resolved ID.
Не переносить raw exception message с URI/query в штатный diagnostic log;
определить безопасные категории ошибок и способ расследования через request ID.
Изменение существующего log contract описать в release notes и обновить его тесты.

Готово, когда при включённой диагностике видна причина каждого рассмотренного кандидата,
а изменение статуса адаптером сохраняет оба статуса.
При выключенной диагностике штатные запросы не создают per-request log; ошибки остаются наблюдаемыми.
Cases с email/token в query, resolved path и exception message не раскрывают их значения.
Проверяются одиночный и два последовательно расположенных фильтра.

### DX-05. Rollout и данные

Показать `catalog_read` и `catalog_write` как два builder/filter после общих security checks.
Actions должны быть непересекающимися; документация объясняет порядок и проблему пересечения.
На первом этапе не добавлять route-level flags или процентное распределение.

Для каждого сценария перечислить владельца записи, источник чтения Yii/backend,
условия допустимости bypass, совместимость новых данных и условия отключения флага.
Проверить create → backend list → legacy bypass list → flag off → legacy read на одной сущности.
Не считать отключение флага откатом данных. При несовместимом новом формате данных явно запрещать обещание
безопасного routing rollback до готовности отдельного data plan.

Готово, когда четыре сочетания flags дают ожидаемого исполнителя и ровно одну бизнес-операцию,
а результат записи виден всем разрешённым читателям.
Reload flags и продолжение уже начатого запроса описаны и проверены на примере.

### DX-06. Callback без скрытой смены контракта

`afterAttempt()` сохраняет нынешнее поведение: исключение передаётся host handler.
Источник: [UpstreamTransport.php](../../../src/UpstreamTransport.php),
`testHookFailureIsVisible` и `testHookTransportExceptionIsNotMistakenForAnUpstreamFailure`.
Показать необязательный metrics callback с локальным `try/catch` и безопасным логированием ошибки.
Для стандартных метрик прежде использовать DX-04.

Готово, когда после одной backend write ошибки необязательного metrics sink не меняют успешный ответ,
а ошибки обязательного hook по-прежнему передаются host handler.
Ни один вариант не выполняет retry или legacy replay.
Если пользователи повторно пишут одинаковую защиту, отдельно рассмотреть новый observer;
решение включает формат результата, политику исключений и путь совместимости, а не молчаливый catch старого hook.

### DX-07. Проверка перед запуском и runbook

Сначала дать пример deployment check с доступом к фактической конфигурации приложения.
Не предполагать, что библиотека знает bootstrap, secret store и reload process любого Yii host.
Проверить origin, route shape, header names/values, TLS setting, callbacks и наличие класса/interface адаптера.
Недопустимые timeout, которые runtime заменяет default, показывать предупреждением.
Проверка работает при выключенном флаге и не отправляет HTTP-запросы, не вызывает readers/hooks,
не создаёт экземпляры business adapters и не запускает legacy actions.
Проверка доступности — отдельный opt-in read-only endpoint, не write route.

Публичный validator добавлять только после пилота, если recipe требует дублирования правил runtime.
Его дизайн должен переиспользовать правила, возвращать несколько адресных ошибок без secret values
и не вводить второй configuration framework. Проверка класса не доказывает успешность его конструктора.

Runbook объясняет: что означает timeout после write, где проверить факт операции,
как использовать прежний idempotency key по backend-контракту, выключить нужный flag,
reload config и проверить следующий запрос. Ни probe, ни preflight не гарантируют будущий успех записи.

### DX-08. Доверенный контекст и идемпотентность

Tenant определяет приложение после авторизации; server-owned header не берётся из client allowlist.
Показать подмену входящего tenant header и серверное значение, которому доверяет backend.
Новый dynamic-header callback рассматривать только если пример выявит ограничение существующей настройки.
При его добавлении нужно отдельное решение о runtime validation и исключениях.

Idempotency принадлежит backend: scope ключа, fingerprint запроса, сохранённый результат,
конфликт повторного ключа с другим телом и срок хранения задаются его контрактом.
Прокси только пересылает ключ; не генерирует новый при повторе и не дедуплицирует операции.

Готово, когда подмена tenant не меняет доступный набор данных,
а потеря ответа после записи и явный повтор с прежним ключом создают один объект.
Guest context и отсутствие требуемого tenant дают предусмотренный host/backend контракт.

### DX-09. Проверка результата для потребителя

Добавить простую таблицу contract cases и runner на существующих средствах, без нового test DSL.
Cases содержат ожидаемые статус, JSON-типы, envelope и значимые headers.
Off/on запускаются на одинаковых изолированных начальных данных;
переменные поля исключаются только по явному списку.
Последовательности write/read проверяются отдельно: сравнение одних статических GET не доказывает совместимость.

Включить большой строковый ID `9007199254740993`, пустой объект/массив, malformed backend response,
field validation errors и неизвестный результат write.
Для утверждения о браузерном клиенте нужен case его настоящего decoder;
PHP-тест не доказывает сохранение точности JS number.

Цель пилота: новый Yii-разработчик и backend-разработчик запускают пример и находят причину bypass
без устных подсказок автора. Измерить время первого запроса и число вопросов.
Плановая цель — до 15 минут после установки зависимостей; результат пока не измерен.
Не называть сценарные роли в этом документе уже проведёнными пользовательскими интервью.

## Порядок реализации

1. DX-01, DX-02, DX-03 и базовые DX-09: законченный пример и доказательство клиентского контракта.
2. DX-04: диагностика, безопасность журнала и корректная композиция фильтров.
3. DX-05 и DX-06: управляемый rollout, данные и recipe необязательных hooks.
4. DX-07 и DX-08: эксплуатация, проверка настройки и backend integration recipes.
5. Пилот с настоящими пользователями; затем решение о validator, observer и dynamic headers.

Каждый этап — отдельное reviewable изменение с доставляемыми примерами и целевыми проверками.
Для изменений runtime сохраняются PHPStan, Soda, Pint, Rector, coverage и mutation gates.
Для docs/examples проверяются именно опубликованные исходники и команды; snapshot кода не заменяет smoke.
Перед объявлением готовности проверить удалённый CI текущего коммита, а не только локальные инструменты.
